# 02 - Validate every CsvViewer request before dispatch

**What to build:** Desktop and web accept and reject the same CsvViewer requests. Malformed requests fail before dispatch with one sanitized message and cannot change Working CSV data. Valid actions retain their existing behavior, including Comparison validation and close confirmation.

**Blocked by:** 01 - Consistent, sanitized failure messages. Malformed requests must use the completed failure translation and desktop transport. Effect workspace adoption ticket 04 is a transitive prerequisite through ticket 01.

- [ ] Define Effect Schema values for every CsvViewer operation and nested request structure, including dialect options, sort, filters, Comparison requests, and confirmed close impact. Derive request types from the schemas without changing field names or shapes. Use Effect `4.0.0-rc.115` as the API authority.
- [ ] Give each schema constant the same name as its derived type, without a `Schema` suffix. Keep schemas in a separate workspace module and re-export their types only through the renderer-facing contract. Results, events, and capabilities remain hand-written types without runtime decoding. Identifiers remain unbranded strings without format validation.
- [ ] Preserve current renderer inputs: optional fields accept explicit `undefined`, numeric filter values accept `NaN`, and excess keys use Schema's default ignore behavior. Accept readonly schema-derived arrays in consumers instead of applying `Schema.mutable`. New structural validation must not reject requests the current renderer sends.
- [ ] Validate presence, value kinds, literal choices for placement, sort direction and filter operators, and non-negative integer offset and limit for Working CSV row windows. Keep the maximum row-window limit check and its existing `1000 or less` message in the store.
- [ ] Preserve domain validation and its precedence. Comparison window offset and limit decode as numbers, leaving `invalid-window` after `comparison-not-found` and `result-replaced`. Comparison Key decoding accepts any string array, leaving empty and duplicate key checks to the existing `invalid-key-shape` outcome. Keep selected-row and active-query insertion checks, column-name checks, and last-column deletion checks with their current messages.
- [ ] Add the owner-side `receive` entry accepting an unknown payload and returning a Promise. Decode before dispatch; the typed `call` delegates to it. Desktop IPC passes its raw payload to `receive` without a request cast. Web and shared contract suites continue through `call`, exercising the same decoder.
- [ ] Reject malformed payloads, including unknown operations, with `Malformed CSV Viewer request.` through ticket 01's failure translation and transport. Do not expose Schema issue text. Decode before using a request operation as a span name or log message. A decode failure records only the fixed stage `csv-viewer.request`, the allowlisted outcome `malformed-request`, and no identifiers or request content.
- [ ] Compare decoded confirmed `CloseImpact` values using `Schema.toEquivalence` so object key order cannot cause repeated close confirmation. Keep the existing comparison for `WorkspaceCloseImpact`, which is not decoded.
- [ ] Remove the old request-envelope guard, transport payload aliases, unsafe request cast, unsupported-operation fallback, unreachable dispatch defaults, and row-window integer validator once decoding replaces them. Remove the preload event guard and its unused event and intent guard helpers, retaining the intent list only if another consumer needs it. Delete tests that only exercise the removed guards.
- [ ] Run shared CsvViewer contracts against native DuckDB and DuckDB-Wasm without weakening assertions. Change the unsupported `workspace.dispose` request assertion to expect `Malformed CSV Viewer request.`; existing declared outcomes and deliberate validation messages stay unchanged.
- [ ] Add a decoding contract case covering an unknown operation, a missing required field, a wrong value kind, an unknown placement, and a negative Working CSV row-window offset. Assert the exact sanitized message and unchanged Working CSV state and data revision. Extend diagnostics coverage to prove malformed input produces the fixed stage and outcome without request content.
- [ ] Verify decoded close confirmation completes and still prompts when the impact changes. Reuse existing lifecycle coverage where it proves these guarantees. Exercise open, query, edit, Comparison, and close behavior on desktop and web with the verification skill.
- [ ] Run the required type, lint, and test checks and both builds. Verify the desktop renderer still does not bundle Effect and that the transport behavior and failure classification from ticket 01 remain intact.
