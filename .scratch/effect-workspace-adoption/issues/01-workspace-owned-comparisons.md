# 01 - Run Aligned Comparisons under the workspace Effect runtime

**What to build:** Desktop and web run Aligned Comparisons as work owned by the workspace. Starting a Comparison returns promptly while computation continues. Cancellation, dependent Working CSV close, and workspace disposal settle the underlying work and cleanup before releasing resources. Maintainers get one execution model for comparison, with Effect composed internally and promises used at the renderer-facing transport interface.

**Blocked by:** None. Can start immediately.

This is the first slice of the parent spec, "Effect adoption for workspace operations and observability." Implement the workspace ownership changes through the complete comparison flow on both runtimes. Local tracing and structured diagnostic output are delivered by ticket 02; CSV open/reopen migration is delivered by ticket 03.

- [x] Each workspace owns one Effect ManagedRuntime, configured at workspace construction using the installed Effect release's supported APIs. Use Effect's runtime directly; keep the application adapter limited to entry execution, transport outcome translation, and lifecycle integration rather than adding a custom execution framework.
- [x] Supply real host and database dependencies at workspace construction through Effect service definitions and Layers where construction or resource ownership requires them. Reuse the existing native and web adapters. Keep dependency construction details out of operation interfaces and keep pure helpers as ordinary functions. The comparison implementation must accept the same dependency definitions in application and test compositions without constructing another runtime internally.
- [x] A shared entry adapter executes migrated internal Effects and exposes the existing promise-based CsvViewer contract. Preserve requests, results, events, capabilities, and workspace-owner confirmation and disposal behavior. Effect values and live resources remain within the owning process.
- [x] Make the complete asynchronous comparison workflow Effect-based: attempt acquisition, key validation, snapshot computation, result-window reads, cancellation coordination, snapshot retirement, close, and executor disposal. In particular, the ComparisonExecutor methods for result reads, snapshot removal, and disposal return Effects alongside its existing Effect-based attempt interface. Pure calculations can remain synchronous.
- [x] Comparison orchestration composes those Effects and starts background work within workspace ownership. Remove independent execution calls and internal Effect-to-Promise round trips from migrated modules. Adapt promises from existing driver and unmigrated workspace dependencies at their integration points with typed failures and explicit cancellation behavior; converting all unrelated host or database methods is outside this ticket.
- [x] Define workspace, attempt, and published-result lifetimes separately. The workspace owns admitted background work and shared dependencies. Each Comparison attempt has a scope for its temporary connections, leases, and staging cleanup, released when that attempt settles. One runtime must not cause all temporary resources to remain alive until workspace disposal.
- [x] Successful publication transfers snapshot ownership to the Comparison before the attempt scope closes. The result stays readable after attempt completion, until replacement or close retires it and outstanding readers finish. Failed or interrupted attempts release their staging resources without invalidating an existing published result. Make this ownership transfer explicit in code and documentation.
- [x] An accepted Comparison survives completion of its begin request, retains its operation identity, and emits the existing terminal outcome. Invalid Comparison Keys, source-change races, refresh, swap, and closing a Comparison preserve existing behavior.
- [x] When cancelling a Comparison or closing dependent work, request cancellation for cancellable driver operations and await driver settlement before releasing connections, source leases, or result resources. For non-cancellable driver operations, await query settlement without interruption before cleanup. Preserve the existing cancellation-request acknowledgement and terminal-event behavior; requesting cancellation and completing cleanup are distinct. Preserve native and Wasm cancellation behavior; interruption of a promise alone is insufficient.
- [x] Workspace disposal rejects new admission, interrupts and awaits Comparison work, and preserves completion guarantees for already admitted CSV opens, reads, and edits. Dependent resources settle before the database closes. Concurrent disposal remains idempotent.
- [x] Expected comparison and database failures remain explicit in the internal Effect error types through orchestration, result reads, and retirement. Translate failures into existing public outcomes or rejections at the transport or event projection interface. Preserve cancellation and invalid Comparison Keys as existing product outcomes; unexpected defects remain distinguishable from expected failures.
- [x] Cleanup failures remain visible and retain the ownership information needed by existing retry or disposal behavior. Account for finalizer failures in Effect causes as well as typed operation failures, preserving the original failure when cleanup also fails. Do not turn routine recoverable operation errors into defects merely to erase an error type.
- [x] Retain shared-table leases and artifact ownership where required. Keep pure comparison rules and presentation as ordinary functions, and limit host or database adapter changes to the needs of this migration.
- [x] Remove superseded comparison orchestration and temporary migration shims. Update comments and architecture documentation to describe the final ownership model. Keep usable existing failure reporting until ticket 02 replaces it.
- [x] Verify success, invalid Comparison Key, source-change races, cancellation, dependent close, and disposal through existing CsvViewer requests, events, and workspace-owner operations on both native DuckDB and DuckDB-Wasm. Extend existing contract cases only for distinct missing guarantees.
- [x] Prove the lifetime distinctions through existing contract observations: begin returns before background completion, published results remain readable after attempt cleanup, failed or cancelled refresh preserves the prior result where the existing contract requires it, and retirement waits for admitted result readers. Check resource release with existing observations rather than inspecting scope or runtime internals.
- [x] Use existing controlled executors and narrow driver tests to verify each supported adapter path: cancellable operations receive a cancellation request and settle before cleanup, while non-cancellable operations settle without interruption before cleanup. Cover the paths each adapter supports; a separate suite for unsupported paths is not required. Use synchronization barriers rather than timing sleeps, and assert behavior rather than private maps, Effect combinators, or fiber identifiers.
- [x] Demonstrate comparison computation, cancellation, and workspace close through the app verification skill on desktop and web. Run required type, lint, and relevant test checks and resolve observed failures.

**Completion evidence:** Both runtimes preserve the comparison contract. One workspace-owned ManagedRuntime executes the complete asynchronous comparison workflow with dependencies supplied at construction and explicit internal failure types. Temporary attempt resources settle promptly while published results retain their required lifetime. Background work survives begin returning, and no Comparison work uses released resources after cancellation or workspace disposal. Code review confirms that migrated orchestration has no independent runtimes or Effect-to-Promise round trips; contract tests prove the observable behavior.
